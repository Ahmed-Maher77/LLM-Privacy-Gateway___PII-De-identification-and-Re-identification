Part 3: Deep Dive into findNames Heuristics & Boundary Logic
Salma: Yes! findNames uses lists.given as an initial anchor. But if a word like "May" or "Will" passes isGiven(), the function checks isEnglishWord(first). If isEnglishWord returns true, it immediately aborts redacting it as a standalone single name.

Tarek: Exactly. But yesterday, someone passed a full name containing an unlisted Arabic surname particle: "Omar el Sayed". The engine successfully recognized "Omar" as a listed given name, allowed the lowercase particle "el", but then failed on "Sayed" because the custom dictionary missed the entry.

Omar: Right! So we modified the look-ahead loop inside findNames:

TypeScript
for (let j = i + 1; j < ws.length && j - i < 6; j++) {
  if (!adjacent(text, ws[j - 1], ws[j])) break;
  const w = ws[j].text;
  if (PARTICLES.has(w.toLowerCase()) && !isCapitalised(w)) continue; // Allows "el", "bin", "van"
  if (!isNameShaped(w) || !isCapitalised(w) || isAllCaps(w)) break;
  if (!(isSurnameLike(w, l) || !isEnglishWord(w))) break;
  last = j;
}
Salma: Ah! So even if "Sayed" isn't in surnames.txt, because it is capitalized, name-shaped, and not a standard English dictionary word, the look-ahead window attaches it to "Omar" to capture the complete full span "Omar el Sayed".

Tarek: Spot on, Salma. That’s the crucial difference: detectPredefined is a deterministic exact matcher, whereas findNames uses dictionary lookups as an anchor to dynamically scan and attach unlisted surnames.

Part 4: Regex Unicode Boundaries & Span Sorting Deduplication
Nour: Tarek, from a compliance view, how do we guarantee that when we combine matches from detectPredefined, findNames, WinkNLP, and Presidio, we don't end up with overlapping spans or corrupted character offsets?

Tarek: That comes down to two specific modules: our Unicode Boundary Regex and our Span Deduplication Loop.

Omar, explain how we construct the dynamic pattern in loadPatterns().

Omar: Right. When building dynamic regular expressions from our lists, we sort terms by length descending (b.length - a.length) so "Sarah Johnson" always evaluates before "Sarah". Then we wrap the pattern in Unicode lookarounds instead of standard \b:

JavaScript
new RegExp(`(?<![\\p{L}\\p{N}_])(?:${alternatives.join("|")})(?![\\p{L}\\p{N}_])`, "giu")
Salma: Because standard \b only recognizes ASCII English letters, right?

Omar: Exactly! Standard \b fails completely on non-English characters or accented names like "José" or "سارة". By using \p{L} (Unicode Letter) and \p{N} (Unicode Number) inside lookbehinds (?<!...) and lookaheads (?!...), we ensure that "Sarah" matches in "Hello Sarah." but never inside "Sarahville".

Tarek: And once all layers emit their raw spans, we pass them through our 3-tier sorting comparator:

JavaScript
const sorted = [...spans].sort(
  (a, b) =>
    a.start - b.start ||
    (b.end - b.start) - (a.end - a.start) ||
    LAYER_ORDER.indexOf(a.source) - LAYER_ORDER.indexOf(b.source)
);
Salma: Let me double-check my understanding of those tie-breakers:

a.start - b.start: Orders spans from left to right across the document.

(b.end - b.start) - (a.end - a.start): If two spans start at the exact same character index (like "John" at [0, 4] and "John Smith" at [0, 10]), the longer span wins and comes first.

LAYER_ORDER: If start and length are identical across two engines, the most trusted layer (e.g., predefined over wink) wins.

Tarek: Perfect summary! And right after sorting, our merging loop iterates over sorted. If span.start < last.end (an overlap), it merges them by taking Math.max(last.end, span.end) and slicing the exact updated text from the raw document. Zero character drift, zero double-redaction bugs.

Part 2: Bottleneck Root Cause — Database Lock Contention
Hassan: Okay, let's dive into the technical details. Layla, walk us through what happened at the database level during peak load.

Layla: Absolutely. When users added an item to their cart, our handler initiated an explicit transaction block:

SQL
BEGIN TRANSACTION;
SELECT * FROM inventory WHERE product_id = $1 FOR UPDATE;
UPDATE cart_items SET quantity = quantity + 1 WHERE cart_id = $2;
COMMIT;
Mariam: Wait, FOR UPDATE locks the specific row in the inventory table, right?

Layla: Exactly. During high concurrency on popular items—like the electronics bundle discount—hundreds of incoming requests were competing for the row lock on a single product_id.

Karim: Which caused connection pool exhaustion in our Node.js API pods! The API threads were sitting idle waiting for PostgreSQL row locks to release.

Hassan: Exactly right. Holding pessimistic row locks in a Web request lifecycle is an anti-pattern for e-commerce carts. We should move inventory reservation to an asynchronous queue or switch to optimistic concurrency control using version checks.

Part 3: Architectural Solution — Redis Atomic Counters & Asynchronous Reservation
Hassan: Here is the proposed refactoring strategy for the Cart API service:

[ Client Request ] 
       │
       ▼
[ API Gateway / Node.js ] ──► (INCRBY / DECRBY) ──► [ Redis Atomic Inventory ]
       │                                                    │
       ├─ (Fast Validation ACK)                             │ (Success)
       ▼                                                    ▼
[ RabbitMQ Event ] ───────────────────────────► [ Worker Service ]
                                                            │
                                                            ▼
                                                    [ PostgreSQL Sync ]
Layla: I like this approach. By shifting stock reservation to Redis using DECRBY and atomic Lua scripts, we process inventory decrement in sub-millisecond memory calls instead of disk-backed SQL locks.

Karim: And if stock drops below zero, the Lua script instantly rejects the transaction at the Redis layer before it ever touches our database cluster.

Mariam: How does this impact the frontend experience, Hassan? If inventory reservation is async, how do we inform the user if an item becomes out of stock during checkout?

Hassan: Great point, Mariam. The initial Redis check is synchronous and returns an immediate status to your React client within 50ms. The asynchronous part is just the background persistence to PostgreSQL via RabbitMQ workers.

Mariam: Perfect! That means the UI can keep optimistic UI updates without risk of ghost inventory errors.

Part 4: Frontend State & Optimistic UI Strategy
Mariam: On the frontend side, we are using Redux Toolkit with RTK Query. Right now, when a user clicks "+1", we disable the button until the API responds.

Layla: Which feels sluggish when network latency rises above 300ms.

Mariam: Exactly. We plan to roll out optimistic updates:

JavaScript
const addCartItem = build.mutation({
  query: (item) => ({ url: '/cart/add', method: 'POST', body: item }),
  async onQueryStarted(item, { dispatch, queryFulfilled }) {
    const patchResult = dispatch(
      cartApi.util.updateQueryData('getCart', undefined, (draft) => {
        const existing = draft.items.find(i => i.id === item.id);
        if (existing) existing.quantity += 1;
      })
    );
    try {
      await queryFulfilled;
    } catch {
      patchResult.undo(); // Rollback on API failure
    }
  },
});
Hassan: Clean implementation. If the API succeeds, the state remains seamless; if it fails (e.g., stock depleted), the UI safely rolls back the local state and triggers a toast notification.
